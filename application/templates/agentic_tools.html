Agentic SQL & routing

Description

When the Model's Words Become Database Queries

An agentic assistant does more than talk: the application reads its reply, finds tool calls in it, and runs them. In this lab a catering routing assistant can look up drivers' private routing tokens. The server scans every reply for tool lines and turns each one into a SQL query, so whoever steers the model's text steers the query.

Scenario: You are on the catering operations team during a busy lunch rush. Dispatch asks the assistant for routing details, but a malicious insider wants to pull another teammate’s private routing token to reroute deliveries.

Tools. The assistant can emit RUN_ROUTE_LOOKUP("…"), LIST_SQL_TABLES(), or RUN_ROUTE_TABLE_LOOKUP("…", "…"). The server runs up to eight of them per reply, wherever they appear, including inside explanations or code blocks. The lookup fragment is placed into WHERE username LIKE '%fragment%'. Quotes in the fragment are escaped, so breaking out of the string or appending a UNION does not work at any tier. The weakness is that the lookup is not limited to the person asking: any fragment that matches another username, or a wildcard such as %, returns that user's row.

Defense tiers F0–F4 add controls one at a time, and each tier keeps the filters of the tiers below it:

  • F0: no filtering; the fragment reaches the routing_flag table as is.
  • F1: rejects SQL keywords, the wildcards % and _, any fragment containing bob (including spaced-out spellings), and fragments with fewer than three letters or digits.
  • F2: lookups go to a randomly named copy of the table hidden among decoys; LIST_SQL_TABLES() reveals the names.
  • F3: each user's row sits in its own table; plain RUN_ROUTE_LOOKUP is disabled and RUN_ROUTE_TABLE_LOOKUP needs an exact table name.
  • F4: F3 plus a character allowlist on the fragment.

The tool path leaks another user's token at F0. From F1 upward the filters reject every fragment that could match the other driver, so use those tiers to read the rejection messages and see what each control stops.

Solve: get another user's routing token (format RT-…) to appear in the assistant's reply together with the tool output, then press Verify solve. You act as the user you are logged in as, or as alice when not logged in, so for alice the target is Bob's token.

Seeing the SQL. Each API response carries a generated_sql array with the queries that ran. The chat does not display it; open your browser's developer tools, go to the Network tab, and inspect the response of /api/catering-sql/chat.

Model notes. The Free Model tab needs a local model pulled from Lab Setup; without one the assistant replies Error: Ollama status 404. The default small model (llama3.2:1b) often writes a raw SELECT statement or a malformed tool line, which the server ignores. Ask it to output only the tool line, retry, or use a larger model such as mistral:7b.

This lab maps to two OWASP Top 10 for LLM risks: LLM05: Improper Output Handling, because model text is executed as tool calls without checking it against what the user may do, and LLM06: Excessive Agency, because the tool can read every user's data while acting for one user. See Mitigation Strategies for a tenant-scoped tool path you can enable to compare behavior after defenses.

The vector / RAG poisoning counterpart for the same fictional catering org is on Data and Model Poisoning → RAG poisoning lab.

Mitigation Strategies

Hardened tool path (tenant scoped)

With hardened enabled, the server ignores the fragment the model supplies and returns only the current user’s own row, whatever the model asked for. Only RUN_ROUTE_LOOKUP is honored in this mode; LIST_SQL_TABLES() and RUN_ROUTE_TABLE_LOOKUP are not executed. The authorization decision is made by the server, not by the prompt or the model. Use this after you have tried the exploit in Demonstration so the interactive section stays focused on the vulnerable path.

Toggling hardened resets the corresponding chat thread.

Mitigation checklist

  • Authorize in the tool, not in the prompt: derive the tenant or user from the authenticated session and apply it inside every tool, regardless of the arguments the model sends.
  • Structured tool calls: use the provider's function-calling interface with a strict argument schema instead of pattern-matching tool names in free text, so prose or quoted examples are never executed.
  • Parameterized queries only: bind model-supplied values as parameters and never let the model choose table names, columns, or operators.
  • Least privilege: give the tool's database role read access to the caller's rows only (views or row-level security), so a bad query has nothing extra to return.
  • Do not rely on blocklists: keyword and name filters such as F1 are easy to get wrong and hide the missing authorization check rather than fix it.
  • Check results before returning them: drop rows that do not belong to the caller and alert on secrets in outbound text.
  • Limit and log tool use: cap tool calls per turn and record each call with the user, arguments, and executed SQL.

Defense Playbook (Incident Response)

Detect: assistant replies containing foreign RT-… tokens; SQL logs showing broad LIKE patterns from chat traffic.

Contain: disable dynamic SQL from LLM; switch to read-only canned queries.

Eradicate: revoke over-broad DB roles; remove string-concatenated SQL helpers.

Recover: ship parameterized templates + per-tenant authorization on tool results.

Lessons learned: LLM outputs are code; execute them with the same controls as application code.
